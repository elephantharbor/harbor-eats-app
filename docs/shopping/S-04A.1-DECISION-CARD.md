# S-04A.1 Decision card

**Status.** One runtime change. Not deployed. Instacart is not called. Production stays on native shopping with `GROCERY_PROVIDERS = ""`. No migration.

## Plan save and the shopping projection

Saving a dinner plan and projecting it onto the household list are two batches. The plan batch can commit while the list batch does not. A successful plan-save response is allowed only when the projection succeeded, or when no projection was required (the plan is superseded or is not the current plan, or the open list already matched).

`projectSavedPlan` returns `shop_projection_failed` when the required projection does not land. The HTTP body is `{ ok: false, error: "shop_projection_failed", dinner_plan_id }` with status 500. The body has no SQL, constraint name, or driver text.

A revision conflict is retried once, against the list reloaded after the miss. Any other database failure is not retried. A second conflict is also `shop_projection_failed`: the projection did not land, and another attempt inside the same request would not be bounded.

The plan row is already stored when this happens. Detect it by the 500 and `dinner_plan_id`. Recover by projecting that same plan again, or by opening `GET /api/household-shop`, which hydrates through `projectSavedPlan`. Both are idempotent: they rewrite the open list from the plan and do not insert a second plan or a second line for the same ingredient and unit. Creating another plan is not the recovery path. The list read is not treated as success for the save that failed.

The client reloads that saved plan and returns it. A later write in the same gesture still runs: a swap can remove a meal and then add the replacement, and raising the count can still add the meal. The success list toast does not fire for the failed projection. When the gesture is suppressing toasts, the list notice is held and shown when the gesture finishes, unless a later projection in that gesture updates the list.

## Revision-conflict logs

The compare-and-swap miss is `NOT NULL` on `household_shop_cas`. That is expected. It is logged as `{ event: "revision_conflict", scope }` and not as `db_error`. A `NOT NULL` that names another table is a real fault: `db_error` with `kind: "not_null"`, then `shop_save_failed`. Logs stay a class only. They do not include the statement or bound values.

Client-error classes are unchanged. A real household’s `/api/household-shop 409` and `/api/dinner-plans 500` stay actionable. `/api/sessions/me 401` stays expected logged-out.

## Quantity presentation

The shopper-facing amount still comes from `formatShopQuantityAmount`. Display text swaps those fractions for unicode. The accessible string keeps the slash form (`1/8 teaspoon`) and is the `aria-label` when the two differ. Countable `each` / `count` uses the item noun when the name is a plain phrase (`½ lime`, `5 yellow onions`). Anything else stays `each` or the bare amount. Uncommon decimals stay decimals. `0.333` is not shown as `⅓`.

Review labels pass the native list unit (`tsp`, `oz`, `count`) into that same formatter, so the words match the list (`½ oz`, not `½ ounce`). Instacart `line_item_measurements` still use the mapped unit (`ounce`, `each`).

`buy_quantity`, `our_quantity`, and Instacart `line_item_measurements` are the same numbers and units as before. The provider payload does not include the label.
