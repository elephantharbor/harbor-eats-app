# S-08 catalog release

The catalog delta is `data/s08-catalog-delta.sql`, generated by `node scripts/s08-catalog-delta.mjs`.

It inserts the 30 S-08 version rows (`package_revision` `s08-culinary` and `s08-doneness`), replaces child rows for those ids only, retires any other still-published version of those dishes, and updates `catalog_dish.current_version_id` plus the display columns `upsertDish` already writes. `recipe` is inserted with `ON CONFLICT(recipe_id) DO NOTHING`. Version inserts are `INSERT OR IGNORE`, so a second apply does not rewrite `content_hash`. There is no `BEGIN`. `wrangler d1 execute` on a file is atomic per batch, and the delta guard allows only INSERT, UPDATE, and DELETE, so this script is not one transaction. For a few seconds a dish can have two published versions. That window is harmless, and running the file again is idempotent. Household, plan, rating, and shop tables are not in the file.

This branch does not apply it. There is no schema migration. Do not replay `data/staging-catalog-import.sql` onto an existing database.

## Local verification, already run

`node scripts/s08-catalog-delta.mjs` builds two local sqlite databases from the repo catalog and the migrations. It does not open D1.

Against that local database the check is:

- Published global versions before the delta: 250. After the delta: 250. After a second apply: 250.
- `catalog_version` rows after the delta: 305. Unchanged on the second apply.
- Every dish has exactly one published global version, and `current_version_id` points at that row.
- A `dinner_plan_meal` pinned to `rv_maple-mustard-glazed-salmon_v2` still joins to `catalog_version`. That row stays `retired` and still has its ingredient rows. The dish current version is `rv_maple-mustard-glazed-salmon_v3`.
- Household, plan, rating, and shop row counts are unchanged by the delta.

## Preview, then Production

Do this only when S-08 is the release being applied. Do not point `wrangler.staging.toml` at production D1.

Preview database `harbor-eats-cycle1-preview` (`65bc636d-7048-4e58-900b-9066edf6509f`), config `wrangler.staging.toml`:

```
npx wrangler d1 execute harbor-eats-cycle1-preview --remote --config wrangler.staging.toml --file data/s08-catalog-delta.sql
```

No `wrangler d1 migrations apply` step. The schema already has `catalog_version.version_number`.

After Preview, check published count 250, one current published version per dish, and that a pinned older version still resolves (the local verifier's salmon v2 join). Household table counts should be unchanged. Apply the file a second time only as an idempotence check; published count and version count must stay the same.

Pinned-version resolution is a Preview check. Do not look up an individual pinned meal on Production.

Production database `harbor-eats-db` (`23aa3db3-1090-471b-8c8a-b6fe71f5c053`), config `deploy/pages/production/wrangler.toml`, is a separate apply after Preview looks right:

```
npx wrangler d1 execute harbor-eats-db --remote --config deploy/pages/production/wrangler.toml --file data/s08-catalog-delta.sql
```

After Production, check aggregate counts only: published global versions 250, one current published version per dish, and the `catalog_version` row count (305 when the database had 275 versions before this delta). Apply the file a second time only as an idempotence check; those counts must stay the same. Do not join a dinner-plan meal to its pinned version on Production. This branch does not run either command.
